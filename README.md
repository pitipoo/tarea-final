# Atlas Research

Atlas is a single-origin research and investigation platform with a topic-aware visual theme. Its catalog includes the 20 subjects in the U3 system specification. Each field guide switches the site's accent palette to match the subject.

## Run locally

Requirements: Node.js 20 or newer.

```powershell
npm install
Copy-Item .env.example .env
npm start
```

Open `http://localhost:3000`. The app uses a local SQLite database at `data/research.db` by default.

To create the first administrator, set both `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` before starting the server. The password must be at least 10 characters and contain uppercase and lowercase letters plus a number. The bootstrap account is created only when that email does not already exist. All self-service registrations receive the Standard User role; an administrator can promote accounts from the Administration view.

In local development, password-reset links are printed to the server console. For deployed use, configure SMTP and `PUBLIC_URL` so reset links are delivered by email. Recovery requests intentionally return the same response whether or not an account exists.

## Roles and access

- **Guest:** Can browse public research overviews; media and discussions require sign-in.
- **Standard User:** Can save favorites and bookmarks, read and post discussions, and view protected media.
- **Investigator:** Standard capabilities plus permission to create and update research guides, choosing from the catalog's visual themes.
- **Admin:** Investigator capabilities plus account roles, active user sessions, and platform settings.

Role checks and authentication are enforced by the API, not only by the interface. New JWTs expire after 12 hours. The server validates the signing key, user ID, current role, and active session on protected requests. Each account can have at most two active sessions; a third login is rejected until a device is revoked. Password reset tokens are random, hashed at rest, single-use, and expire after 20 minutes.

The browser sends the JWT in the `Authorization: Bearer` header and keeps it in `sessionStorage` for the current browser tab. Restricted cover art is generated by an authenticated endpoint rather than served from the public static directory.

## Deploy on Vercel (temporary demo)

The root `index.js` exports the Express app for Vercel's zero-configuration Express deployment, and `public/` is served from Vercel's CDN. Connect the GitHub repository to Vercel and deploy from the repository root with the included `vercel.json`. Set `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD`, `JWT_SECRET`, and `PUBLIC_URL` in the Vercel project's environment settings. Configure SMTP variables too if you want password-recovery links delivered by email. Redeploy after adding or changing production environment variables.

**This Vercel configuration uses temporary SQLite storage in `/tmp`, as requested for a demo. It is not suitable for real accounts or production data:** the filesystem is ephemeral, and separate serverless instances do not share their session registry. Database contents can disappear on a cold start or deployment, and the two-device limit is not globally reliable across instances. For a persistent production deployment, migrate to a shared Postgres database (for example Neon) before inviting users.

The initial administrator is only created when both bootstrap variables are configured. New registrations are standard users. Never store real passwords or sensitive data in a temporary demo.

## Deploy on Render

The included `render.yaml` provisions a Node web service and persistent disk so the SQLite database survives deploys. Push this folder to a Git repository, create a Render Blueprint from it, and provide the requested bootstrap administrator and SMTP values in Render's environment settings. Confirm `PUBLIC_URL` matches the deployed service URL. The service and frontend run under one origin.

For production password recovery, set `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, and `PUBLIC_URL`. Never commit `.env` or production credentials. Optional server-side Sentry error reporting is enabled by setting `SENTRY_DSN`.
